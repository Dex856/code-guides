0 How to use this guide

Java reduced to exactly what wins coding-round problems: the Collections you actually type, the idioms that make solutions short, and the traps — boxing, equality, overflow — that cost submissions.

Java for LeetCode

Java is verbose on purpose and that verbosity hides traps: an Integer is not an int, == is not equals, a HashMap is not ordered, and int * int overflows silently. This guide covers the subset that solves problems — HashMap, HashSet, ArrayList, ArrayDeque, PriorityQueue, TreeMap, Arrays/Collections helpers — plus the patterns mapped onto those APIs, paste-ready templates for graphs, DSU, binary search and DP, and the pit-falls that separate “works on my machine” from “accepted”.

0.3 The LeetCode Java environment in 60 seconds

LeetCode compiles your submission as a single Solution class (Java 25 on the judge) with the common java.util.* classes already imported, so you can type ArrayList<Integer> or Map.Entry<K,V> without adding imports. There is no main: your method is called once per test case on the same class instance.

// What LeetCode runs for "Two Sum" — the skeleton you fill in
class Solution {
    public int[] twoSum(int[] nums, int target) {
        Map<Integer, Integer> seen = new HashMap<>();   // java.util.* is pre-imported on the judge
        for (int i = 0; i < nums.length; i++) {
            int need = target - nums[i];
            if (seen.containsKey(need)) return new int[]{seen.get(need), i};
            seen.put(nums[i], i);
        }
        return new int[]{-1, -1};                        // never reached for valid input
    }
}   // O(n) time · O(n) space
Three consequences of the judge model — all covered later, all real:
  • Fields persist across test cases. A static or instance field you “reset by intuition” is re-used for the next case. Declare state inside the method (ch. 12.5).
  • No main, no printing. Debugging means the local harness in 1.3 — printing inside a solution is the slowest way to fail.
  • Signatures are fixed. You cannot change the return type to long; convert inside (ch. 2.2).

1 Setup, compile loop, local testing

The three files and four commands you need, and the test loop that catches wrong answers before the judge does.

Setup & the compile loop

You do not need an IDE to solve LeetCode in Java — but you do need a local file you can run in one command, because the judge tells you only “wrong answer”, never why. This chapter sets up a JDK, the exact commands, and a 3-level harness (asserts → randomised stress test → edge-case sweep) that turns a wrong-answer into a reproducible one in under a minute.

1.2 The local harness shape

LeetCode gives you a bare method with no main. Locally, wrap it yourself: keep the Solution class byte-for-byte identical to what you submit, and put all testing in a separate class so nothing you add for debugging can leak into the submission.

// ---------------- Sol.java — the part you paste into LeetCode ----------------
class Solution {
    public int[] twoSum(int[] nums, int target) {
        java.util.Map<Integer, Integer> seen = new java.util.HashMap<>();
        for (int i = 0; i < nums.length; i++) {
            int need = target - nums[i];
            if (seen.containsKey(need)) return new int[]{seen.get(need), i};
            seen.put(nums[i], i);
        }
        return new int[0];
    }
}

// ---------------- Main.java — local only, never submitted --------------------
public class Main {
    public static void main(String[] args) {
        Solution s = new Solution();
        check(java.util.Arrays.equals(s.twoSum(new int[]{2, 7, 11, 15}, 9), new int[]{0, 1}));
        check(java.util.Arrays.equals(s.twoSum(new int[]{3, 2, 4}, 6),        new int[]{1, 2}));
        check(java.util.Arrays.equals(s.twoSum(new int[]{3, 3}, 6),           new int[]{0, 1}));
        System.out.println("all asserts passed");
    }
    // assert() is disabled unless -ea is passed, so use an explicit helper instead
    static void check(boolean ok) { if (!ok) throw new AssertionError("failed"); }
}
Trap: assert x == 4; does nothing by default — Java disables assertions unless you run with java -ea. Use an explicit check(...) helper (above) or always pass -ea.

1.3 The 3-level test loop

LevelWhat you writeWhat it catches
1 · ExamplesEvery sample from the problem statement, plus the empty and size-1 cases. Wrong output on the happy path; null/empty handling; off-by-one on the last element.
2 · Brute force + random stressA slow-but-obviously-correct method, then 1,000 random small inputs comparing both outputs.Everything subtle: boundary conditions, duplicate handling, tie-breaking, overflow on small-but-nasty values.
3 · Scale & safetyOne max-size random input with a stopwatch; then re-run the samples after changing nothing.TLE (wrong complexity), StackOverflowError, quadratic hidden inside a loop, and accidental reliance on test order from leftover fields.
 
// Level 2: randomised stress test — the highest-value 20 lines you will ever write
static void stress() {
    java.util.Random rnd = new java.util.Random(12345);      // fixed seed -> reproducible
    Solution s = new Solution();
    for (int t = 0; t < 1000; t++) {
        int n = 1 + rnd.nextInt(8);
        int[] a = new int[n];
        for (int i = 0; i < n; i++) a[i] = rnd.nextInt(21) - 10;   // includes negatives
        int target = rnd.nextInt(41) - 20;
        int[] fast = s.twoSum(a, target), slow = brute(a, target);
        if (fast.length != slow.length || (fast.length == 2 &&
            !(fast[0] == slow[0] && fast[1] == slow[1]))) {
            System.out.println("MISMATCH on " + java.util.Arrays.toString(a) + " target=" + target);
            System.out.println("fast=" + java.util.Arrays.toString(fast) + " slow=" + java.util.Arrays.toString(slow));
            return;
        }
    }
    System.out.println("stress passed");
}
static int[] brute(int[] a, int t) {                          // O(n^2), obviously correct
    for (int i = 0; i < a.length; i++)
        for (int j = i + 1; j < a.length; j++)
            if (a[i] + a[j] == t) return new int[]{i, j};
    return new int[0];
}
Randomise values, not just sizes. Negative numbers, zero, duplicates, and the extreme of the allowed range expose more bugs than 10,000 well-behaved cases. Generate values in [-10, 10] first; if that passes, widen to the real constraints.

1.4 Timing: what Java can do in a second

Judges allow roughly 1–3 s per test file, and LeetCode runs a batch of cases. Java is typically 2–5× slower than C++ for the same algorithm, mostly because of bounds checks, memory indirection and boxing. Practical planning numbers for the judge machine:

2 Types, numbers, boxing

The number-one source of wrong answer in Java submissions is not the algorithm — it is an int that overflowed, an Integer compared with ==, or a NULL that got unboxed.

Types & numbers without landmines

Java has two parallel worlds — primitives (int, long, char, double…) and reference types (Integer, Long, Character…). Collections only store the second world, so every value that enters a List or Map is boxed and unboxed behind your back. This chapter makes that cost and those traps visible, then fixes the arithmetic rules that quietly break solutions.

2.2 Overflow — the silent wrong answer

Java arithmetic never tells you it overflowed: int ops wrap around modulo 232. In C++ the same wrap is undefined behaviour; in Java it is defined and therefore quieter.

int a = 100_000, b = 100_000;
System.out.println(a * b);            // 1410065408  ← wrong! (10^10 mod 2^32)
System.out.println((long) a * b);     // 10000000000 ← correct: one operand long promotes the expression
long wrong = a * b;                   // ❌ still 1410065408: the multiplication already happened in int
long right = (long) a * b;            // ✅ widen BEFORE multiplying

// summing an array of 10^5 values up to 10^9 each -> 10^14: needs long
int badSum = 0;                       // ❌ overflows
long goodSum = 0; for (int v : arr) goodSum += v;

// midpoint: avoid lo + hi overflow when lo, hi are near Integer.MAX_VALUE
int mid = (lo + hi) / 2;              // ❌ overflow
int mid2 = lo + (hi - lo) / 2;        // ✅

// detect overflow explicitly when you must stay in int
try { int x = Math.multiplyExact(a, b); }
catch (ArithmeticException e) { /* overflow */ }

2.4 Boxing, unboxing and the Integer cache

Collections store references. List<Integer> means an array of pointers to Integer objects, so 1 becomes a heap object, costs ~16 bytes instead of 4, and is fetched through a pointer.

List<Integer> xs = new ArrayList<>();
xs.add(5);                       // autoboxing: int -> Integer.valueOf(5)
int y = xs.get(0);               // auto-unboxing: Integer.intValue()

// The cache trap: valueOf caches -128..127 (Boolean, Byte, Short, Character similarly)
Integer a = 127, b = 127;
System.out.println(a == b);      // true  — same cached object
Integer c = 128, d = 128;
System.out.println(c == d);      // false — two different objects!
System.out.println(c.equals(d)); // true  — always compare wrappers with equals

// NPE: unboxing null throws
Map<String,Integer> freq = new HashMap<>();
freq.put("a", null);
int n = freq.get("a");           // ❌ NullPointerException
int m = freq.getOrDefault("a", 0);  // ✅ 0

// Integer.compare is the overflow-safe comparator
Integer.compare(a, b);           // ✅
// a - b as a comparator ❌ overflows for extreme values (Comparator contract violated)
Trap: map.get(key) + 1 on a missing key throws NPE; map.get(key) == other on Integer values compares references for values outside the cache. Idiomatic fix: map.merge(k, 1, Integer::sum) or map.put(k, map.getOrDefault(k, 0) + 1).

2.6 Doubles: comparison, precision, rounding

// Read-only reference: the lines below are expression forms, not complete statements.
Math.abs(a - b) < 1e-9                     // ✅ tolerance compare (absolute)
Math.abs(a - b) <= 1e-9 * Math.max(1.0, Math.max(Math.abs(a), Math.abs(b)))   // ✅ relative

// The judge usually accepts a relative/absolute error (LeetCode: 1e-5). Never use == on doubles.
0.1 + 0.2 == 0.3                            // ❌ false (0.30000000000000004)
Double.compare(x, y)                        // ✅ total order, handles NaN/-0.0

Math.sqrt(x)   Math.pow(x, y)   Math.hypot(dx, dy)      // hypot avoids intermediate overflow
Math.floor(d)  Math.ceil(d)    Math.round(d)            // round: half-up, returns long for double
(int) Math.sqrt(n)                         // floor sqrt — watch out at 10^15 with double precision

// integer sqrt without floating point risk
long isqrt(long n) { long r = (long) Math.sqrt((double) n); while (r * r > n) r--; while ((r+1)*(r+1) <= n) r++; return r; }
Why Math.hypot: sqrt(dx*dx + dy*dy) overflows int for large coordinate differences and loses precision for double; hypot is scaled internally. For integer answers prefer squared distances and integer comparisons — no floating point at all.

2.7 BigInteger / BigDecimal — when 64 bits are not enough

NeedUseNote
Factorials, 2n for n > 62, huge FibonacciBigIntegervalueOf, add, multiply, pow, mod, compareTo — no operators

import java.math.BigInteger;   // java.util.* does NOT include the math package

BigInteger f = BigInteger.ONE;
for (int i = 2; i <= n; i++) f = f.multiply(BigInteger.valueOf(i));   // n! exactly
BigInteger m = f.mod(BigInteger.valueOf(1_000_000_007L));
System.out.println(m);                                  // mod of a huge factorial: safe
System.out.println(BigInteger.valueOf(2).pow(200));     // 2^200 exactly, instantly

// BigInteger for nCr when values exceed long
BigInteger nCr(int n, int r) {
    BigInteger res = BigInteger.ONE;
    for (int i = 1; i <= r; i++)
        res = res.multiply(BigInteger.valueOf(n - r + i)).divide(BigInteger.valueOf(i));
    return res;
}
Prefer modular arithmetic over BigInteger when the problem says “answer mod 1e9+7”: BigInteger is correct but 10–100× slower. Use long plus the modular tricks in ch. 10.5.
